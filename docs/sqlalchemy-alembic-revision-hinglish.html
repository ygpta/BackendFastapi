01 · Shuruaat

Database ke basic shabd

  • Database: data rakhne ki jagah; is project mein PostgreSQL.
  • Table: ek jaise records ka collection, jaise tickets.
  • Row: table mein ek record, jaise ek support ticket.
  • Column: record ka ek field, jaise subject ya status.
  • ORM: Python objects ke zariye SQL database ke saath kaam karna.

SQL mein ticket dhoondhne ka ek example:

SELECT id, subject, status
FROM tickets
WHERE id = 42;

SQLAlchemy ORM mein isi ka Python-style roop:

statement = select(Ticket).where(Ticket.id == 42)
record = await session.scalar(statement)

ORM SQL ko khatam nahi karta. ORM tumhare Python expression ko SQL mein badalta hai aur result ko Python object ke roop mein deta hai.

02 · Table ka Python roop

SQLAlchemy model kya hai?

Project ka model Ticket class hai. Ye database mein tickets table ka structure describe karta hai.

class Ticket(TenantScoped, Base):
    __tablename__ = "tickets"

    id: Mapped[int] = mapped_column(primary_key=True)
    subject: Mapped[str] = mapped_column(String(120))
    message: Mapped[str] = mapped_column(Text)
    status: Mapped[str] = mapped_column(
        String(16), default="open", server_default="open"
    )
  • Base: SQLAlchemy ke sab models ka common base aur metadata registry.
  • __tablename__: actual database table ka naam.
  • Mapped[str]: Python mein field ka expected type.
  • mapped_column(...): database column aur uske rules.
  • primary_key=True: row ki unique pehchaan.
  • String(120) aur Text: database column ke types.

Ticket(...) ek Python ORM object banata hai. Ye apne-aap database mein save nahi hota:

ticket = Ticket(
    subject="Login issue",
    message="I cannot log in today.",
)

print(ticket.subject)  # Login issue
Yaad rakho: Pydantic request schema input validate karta hai. SQLAlchemy model table/row represent karta hai. Dono ka kaam alag hai.
03 · Connection aur session

Engine aur SessionFactory

session.py mein engine connection pool banata hai. Pool database connections ko reuse karta hai, taaki har request par naya connection banana na pade.

engine = create_async_engine(
    settings.database_url,
    pool_pre_ping=True,
    pool_size=settings.database_pool_size,
)
SessionFactory = async_sessionmaker(
    engine,
    expire_on_commit=False,
)
  • database_url: database tak pahunchne ka connection address. Secret URL ko logs mein mat dikhana.
  • pool_pre_ping=True: use se pehle check karta hai ki pooled connection abhi zinda hai.
  • SessionFactory: har request ya kaam ke liye naya AsyncSession banata hai.
  • expire_on_commit=False: commit ke baad loaded object ke fields ko turant expire nahi karta.

get_db_session session request ko deta hai aur request khatam hone par close karta hai. Tenant ID bhi yahin verified user se session mein daali jaati hai. 

async def get_db_session(principal):
    async with SessionFactory() as session:
        session.info["tenant_id"] = principal.tenant_id
        yield session
04 · CRUD ka code flow

Create, read, list aur update

CRUD ka matlab Create, Read, Update, Delete. Ticket repository yahan hai: repositories/tickets.py.

Create

record = Ticket(**data.model_dump())
session.add(record)
await session.flush()
await session.commit()

model_dump() Pydantic input ko dictionary banata hai. Ticket(**...) dictionary ke keys ko model constructor ke arguments banata hai. add object ko session mein register karta hai.

Read

statement = select(Ticket).where(Ticket.id == ticket_id)
result = await session.execute(statement)
record = result.scalar_one_or_none()

scalar_one_or_none() ek matching Ticket deta hai ya match na ho to None. Endpoint None par HTTP 404 return karta hai.

List aur pagination

statement = (
    select(Ticket)
    .where(Ticket.id < before_id)
    .order_by(Ticket.id.desc())
    .limit(limit + 1)
)

where filter hai, order_by sorting hai. Ek extra row mangkar code jaan leta hai ki agla page hai ya nahi—har baar total count nikalne ki zaroorat nahi.

Update aur version check

statement = (
    update(Ticket)
    .where(
        Ticket.id == ticket_id,
        Ticket.version == expected_version,
    )
    .values(
        status=new_status,
        version=Ticket.version + 1,
    )
    .returning(Ticket)
)

ID ke saath purana version bhi match hona chahiye. Agar kisi aur ne pehle update kar diya, row match nahi hogi aur app 409 Conflict dega. Isse stale screen se doosre ka update chupke se overwrite nahi hota.

05 · Transaction

add, flush, commit mein farq

Code Asaan matlab Kya final save hua?
session.add(obj) Object ko session ke pending kaam mein jodo. Nahi
await session.flush() Pending SQL database ko bhejo; generated ID mil sakti hai. Abhi nahi, transaction open hai.
await session.commit() Transaction confirm karo. Haan
await session.rollback() Current uncommitted changes cancel karo. Nahi, changes discard hote hain.

Project create ke baad flush() karta hai, kyunki audit record ko ticket ID chahiye. Phir ticket aur audit dono ko ek transaction mein commit kiya jaata hai. Transaction fail hui to dono changes saath rollback ho sakte hain.

Har repository function ko apna commit karna zaroori nahi. Idempotent ticket create mein service ticket aur replay response ko ek saath commit karne ke liye repository ko commit=False deti hai.
06 · Schema ka history

Alembic kis kaam aata hai?

Model code aaj ka desired table structure batata hai. Alembic migration database ko purane structure se naye structure tak le jaane ke step likhti hai. Jaise migration 0001 tickets table banati hai; 0003 status/version columns aur index add karti hai.

revision = "0003"
down_revision = "0002"

def upgrade():
    op.add_column("tickets", ...)
    op.create_check_constraint(...)
    op.create_index(...)

def downgrade():
    op.drop_index(...)
    op.drop_constraint(...)
    op.drop_column(...)
  • revision: is migration ka ID.
  • down_revision: isse pehle ka migration. Is tarah Alembic ko order pata chalta hai.
  • upgrade(): schema ko aage badhata hai.
  • downgrade(): schema change reverse karta hai; column drop karna data delete kar sakta hai, so production mein soch samajhkar.

migrations/env.py models ka Base.metadata Alembic ko deta hai aur settings se DB URL padhta hai. Migration history ko edit/delete mat karo; naya change ho to nayi revision banao.

Important: Production API startup har worker mein create_all() nahi chalata. Compose ka alag migrate job Alembic ko ek baar chalata hai.
07 · Roz ke commands

Migration ka workflow

# Current DB revision dekho
uv run alembic current

# Saari revision history dekho
uv run alembic history

# Model change ke baad migration draft banao
uv run alembic revision --autogenerate -m "add ticket priority"

# Generated migration review karne ke baad apply karo
uv run alembic upgrade head

# Check karo model aur DB schema match hain ya nahi
uv run alembic check

--autogenerate draft banata hai; generated file ko padhna aur test karna tumhari responsibility hai. Har schema change automatically safe nahi hota.

Test safety: test_postgres.py database ko downgrade karke migration dobara chalata hai. Ise sirf disposable test PostgreSQL par chalao—production ya valuable local DB par nahi.
