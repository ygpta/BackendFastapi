Chapter 01

Yeh application actually karti kya hai?

Yeh ek support-ticket API aur tenant-aware agent platform hai. Tenant ko ek customer organization ya alag workspace ki tarah samjho. FastAPI HTTP framework deta hai; tumhara code business rules implement karta hai. PostgreSQL mein tickets, users, sessions, documents, jobs, budgets, events aur audits store hote hain. Durable agent jobs ek alag worker process chalata hai, sirf HTTP endpoint nahi.

Client>Uvicorn / ASGI>Middleware>Router + dependencies>Endpoint>Service / repository>PostgreSQL

Response middleware layers se wapas bahar aata hai. Is diagram ko mental model samjho; iska matlab yeh nahi ki har dependency, har validation step ke baad hi chalegi. FastAPI endpoint call karne se pehle dependency resolution aur request validation coordinate karta hai.

Kahan dekho Zimmedari kya hai Code mein kya milega
main.py App ko assemble karna App factory, middleware, lifespan, routers
api/ HTTP request/response ki boundary Methods, paths, status codes, dependencies
schemas/ Public input/output ka contract Pydantic validation aur serialization
services/ Business operation ke steps jodna Idempotency, budgets, run submission
repositories/ Database mein data padhna/likhna SQL expressions, flush, commit, audit
db/ Database infrastructure sambhalna ORM models, factories, tenant hooks
agents/ aur worker.py Agent jobs execute karna Graphs, checkpoints, leases, recovery

Framework aur apne code ka difference: Uvicorn server hai, ASGI server/app ke beech ka interface hai, Starlette basic web behavior deta hai, FastAPI typed routing aur dependencies jodta hai, aur Pydantic data validate karta hai. SQLAlchemy, JWT authentication, LangGraph aur durable queue additional libraries ya application code hain, FastAPI ke built-in features nahi. Kuch platform endpoints directly SQL chalate hain; har operation repository se hi guzrega, aisa framework rule nahi hai. Layers ka purpose responsibilities samjhana hai.

Chapter 02

Import se app serve hone tak

src/backendfastapi/main.py / exact excerpt 
def create_app() -> FastAPI:
    """Build an isolated app; dependencies and tests can supply external resources."""
    settings = get_settings()
    application = FastAPI(
        title="Support Agent API",
        version="0.1.0",
        description="Support tickets and persistent LangGraph conversations.",
        lifespan=lifespan,
        docs_url=None if settings.environment == "production" else "/docs",
        redoc_url=None,
        openapi_url=None if settings.environment == "production" else "/openapi.json",
    )
  1. backendfastapi.main:app jaise server target ka matlab hai: module import karo aur uska exported app object lo.
  2. Import ke waqt module ka top-level code execute hota hai. Database module import hote hi settings load hoti hain aur engine/session factory construct hote hain.
  3. Module ka app = create_app() factory call karta hai. Factory routes aur middleware register karti hai; registration ke waqt koi request handle nahi hoti.
  4. Phir server lifespan startup enter karta hai. Startup successfully complete hone ke baad requests serve ho sakti hain.
  5. Shutdown par lifespan exit hota hai aur registered resources release hote hain.

title, version aur description API metadata hain. OpenAPI request/response contracts describe karta hai; non-production mein /docs par Swagger UI wahi description dikhata hai. Production mein Swagger UI aur OpenAPI endpoint dono disabled hain, jabki ReDoc har environment mein disabled hai. Documentation hide karna authentication ya access control nahi hai.

Factory ka matlab har resource isolated nahi: har call naya FastAPI object aur per-app metrics banati hai, lekin module-level engine aur SessionFactory replace na karo to shared rehte hain. get_settings.cache_clear() purani settings se pehle ban chuke objects dobara nahi banata.

Chapter 03

Settings kaise load, validate aur cache hoti hain?

src/backendfastapi/core/config.py / exact excerpts
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env", extra="ignore", hide_input_in_errors=True
    )

BaseSettings, pydantic-settings se aata hai. Normal Python class se alag, yeh external sources se configuration values leta hai aur validate karta hai. Yahan relevant priority hai: constructor arguments, phir process environment variables, phir .env, aur last mein defaults. Jaise Settings(log_level="DEBUG") us construction ke liye environment value override karega. Environment names default mein case-insensitive hote hain, isliye LOG_LEVEL, log_level field se map hota hai. Relative .env path process ki working directory se resolve hota hai, automatically is Python file ke folder se nahi.

extra="ignore" unrelated configuration fields ignore karta hai. hide_input_in_errors=True rendered validation errors mein input values accidentally expose hone ka risk kam karta hai; yeh har logger aur har error ke liye universal secret-redaction system nahi hai.

Configuration fields / exact excerpt
environment: Literal["development", "test", "production"] = "development"
log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"
api_key: SecretStr | None = None
auth_enabled: bool = False

Literal sirf listed values allow karta hai. AUTH_ENABLED=true jaisi string Python ke True boolean mein parse hoti hai. SecretStr | None optional secret value batata hai; SecretStr ordinary string representations mein value mask karta hai. Jab kisi library ko actual secret chahiye, code explicitly get_secret_value() call karta hai. Raw value log mat karo. Masking ka matlab encryption nahi hai.

Bounded settings / exact excerpt
access_token_minutes: int = Field(default=15, ge=1, le=60)
refresh_token_days: int = Field(default=7, ge=1, le=30)
requests_per_minute: int = Field(default=120, ge=1, le=10000)

ge ka matlab greater than or equal, aur le ka matlab less than or equal hai. Settings construct hote waqt parsing aur bounds check hote hain. Invalid deployment configuration par Pydantic validation error aata hai; yeh startup/configuration failure hai, client request ka HTTP 422 nahi.

Normalize before field validation / exact excerpt
@model_validator(mode="before")
@classmethod
def normalize_optional_secrets(cls, values):
    # Compose passes empty strings when optional secrets are not configured.
    for key in ("api_key", "openai_api_key", "jwt_secret"):
        if values.get(key) == "":

Yeh model-level validator normal field parsing se pehle raw input badalta hai: empty configured secret ko None banata hai. Uske baad after validator parsed settings object par fields ke combinations check karta hai. Async PostgreSQL driver required hai; chat enabled ho to provider key, auth enabled ho to minimum 48-character JWT secret, aur API key di ho to minimum 32 characters chahiye. Production mein additionally JWT authentication, metrics API key, explicit hosts, non-default database credentials, wildcard ke bina CORS origins aur disabled public registration required hain.

The accessor / exact excerpt
@lru_cache
def get_settings() -> Settings:
    env_file = os.getenv("APP_ENV_FILE")
    if env_file is None:
        return Settings()
    if env_file == "":
        return Settings(_env_file=None)
    path = Path(env_file)
    if not path.is_file():
        raise ValueError("APP_ENV_FILE must point to an existing settings file")
    return Settings(_env_file=path)

APP_ENV_FILE shell ya deployment mein startup se pehle set karo. Unset ho to default .env, nonempty path ho to sirf selected file, aur empty value ho to dotenv loading off hoti hai. Explicit file missing ho to error aata hai. Relative path working directory se resolve hota hai. .env.production naam apne aap production mode nahi banata: file ya process environment mein ENVIRONMENT=production bhi do. Process environment ki values file par priority rakhti hain.

Host par file selection / commands ka example
export APP_ENV_FILE=.env.development
uv run alembic upgrade head
uv run uvicorn backendfastapi.main:app --reload --no-access-log

Production mein preferred path environment/secrets injection hai; APP_ENV_FILE='' file reading disable karta hai. Compose mein --env-file .env.production host par file read karta hai, phir configured mapping ki values inject karta hai. App containers dotenv reading off rakhti hain; host file path container mein automatically nahi milta. API, worker, migrations aur admin command shared loader use karte hain. Deployment examples ke liye production guide dekho.

@lru_cache function ko cache ke saath wrap karta hai, jiska key function ke arguments se banta hai. Is function ke arguments nahi hain, isliye successfully bani settings object ko baad ki normal calls reuse karti hain. Return annotation sirf type batata hai; actual validation Settings() karta hai. Cache har process ka apna hai, workers ke beech shared nahi, aur periodically configuration refresh nahi karta. Concurrent first calls duplicate construction kar sakti hain; isko strict initialization lock mat samjho.

Conceptual usage example / not an additional project function

assert first is second

get_settings.cache_clear()
fresh = get_settings()

Environment variables badalne wale controlled tests mein cache clear karna useful hai. Returned settings mutate mat karo: dusre callers ke paas bhi wahi object hota hai. Database module, app factory, lifespan, endpoints aur worker sab yeh accessor use kar sakte hain. FastAPI ka per-request dependency cache aur yeh process-level cache do alag mechanisms hain.

Chapter 04

Lifespan aur application state ka role

src/backendfastapi/main.py / exact excerpt 
@asynccontextmanager
async def lifespan(application: FastAPI) -> AsyncIterator[None]:
    # Learn: startup/shutdown run once per process, not once per request.
    settings = get_settings()
    configure_logging(settings.log_level)
    application.state.chat_workflow = None
    async with AsyncExitStack() as resources:
        # Registered cleanup runs even if startup or a later resource fails.
        resources.push_async_callback(engine.dispose)

@asynccontextmanager async generator ko async context manager banata hai. yield se pehle ke statements startup hain; context se bahar nikalte waqt cleanup hota hai. AsyncIterator[None] generator ki yielded value ka type describe karta hai. AsyncExitStack cleanup callbacks track karta hai aur reverse registration order mein chalata hai, chahe baad ka initialization step fail hi kyon na ho.

Code tracing configure karta hai aur provider shutdown register karta hai. Shared httpx.AsyncClient tabhi open hota hai, ChatOpenAI tabhi banta hai, aur legacy workflow tabhi attach hota hai jab chat_enabled true aur auth_enabled false ho. Authenticated mode mein generation worker sambhalta hai. Shutdown workflow reference clear karta hai aur registered clients/providers/engine resources close karta hai.

Attach a shared factory / exact excerpt
application.state.session_factory = SessionFactory

Current app request.app se milta hai. Isliye streaming code factory ko request.app.state.session_factory se retrieve karta hai. Yahan reusable factories aur concurrency-safe clients rakho, sab requests ke liye ek hi mutable database session nahi.

Data kahan hai Kab tak rehta hai Project mein example
app.state Ek process ke app instance tak Session factory, metrics, workflow
request.state Sirf ek request tak Middleware ka assigned request ID
Cached settings Cache clear ya process exit tak Configuration object
Database Process restart ke baad bhi durable Tickets, sessions, runs, audits

Jo state attribute set nahi hai usko directly read karoge to AttributeError milega. Error handler getattr(request.state, "request_id", "unknown") se fallback deta hai. State persistent storage nahi, aur processes ke beech synchronization bhi nahi karta.

Chapter 06

Dependency injection: function ke arguments aate kahan se hain?

src/backendfastapi/api/deps.py / exact excerpt
async def get_db_session(
    principal: Annotated[Principal, Depends(get_principal)],
) -> AsyncIterator[AsyncSession]:
    # Learn: the verified Principal supplies tenancy; client JSON cannot choose it.
    async with SessionFactory() as session:
        session.info["tenant_id"] = principal.tenant_id
        session.info["actor_id"] = principal.user_id
        # FastAPI resumes after yield for cleanup; session exit closes/rolls back.
        # Commits remain explicit in the business operation, not in this dependency.
        yield session

Annotated[Principal, Depends(get_principal)] expected Python type aur dependency metadata ko saath rakhta hai. FastAPI pehle get_principal ki dependencies resolve karta hai, phir usko call karke returned value inject karta hai. Function bina parentheses pass karo: Depends(get_principal) ek callable register karta hai. Khud function call karoge to FastAPI ka resolution mechanism bypass ho jayega.

Settings + bearer + auth session>Principal>Scoped business session>Endpoint

Router-level dependency requirement ki tarah run hoti hai, lekin uski returned value endpoint ko automatically nahi milti. Principal chahiye to endpoint parameter mein declare karo. Agar router aur koi doosri dependency dono same principal maangte hain, default per-request caching normally result reuse karti hai. Isse us request ke dependency graph mein duplicate identity checks aur extra rate-limit consumption avoid hote hain.

yield wali dependency pehle resource deti hai aur baad mein cleanup ke liye resume hoti hai. Yahan session context session close karta hai aur uncommitted work rollback karta hai; automatically commit nahi karta. Streaming ke around cleanup timing dependency scope aur framework behavior par depend karti hai. Isliye SSE code poori stream ke dauran transaction hold karne ke bajay polling mein short-lived sessions kholta hai.

Sab kuch har endpoint ke andar hi kyon na banayein?

Dependencies resource lifetime, permissions aur configuration ko ek jagah manage karti hain. Function signature se requirements dikhti hain aur tests app.dependency_overrides se production implementation replace kar sakte hain. Lekin dependencies business services ko replace nahi karti aur explicit transaction boundaries ki zaroorat khatam nahi karti.

claims = jwt.decode(
    credentials.credentials,
    settings.jwt_secret.get_secret_value(),
    algorithms=["HS256"],
    issuer=settings.jwt_issuer,
    audience=settings.jwt_audience,

Allowed algorithm explicitly diya gaya hai. Do alag modes hain: auth_enabled false ho to function legacy API-key path leta hai aur admin role wala service principal return karta hai. Yeh individual user authentication ke barabar nahi. Production mein authenticated mode required hai.

Authentication poochta hai: caller kaun hai? Authorization poochta hai: is caller ko kya karne ki permission hai? Missing/invalid identity par 401, insufficient permissions par 403, aur inaccessible tenant resource par generally 404 aata hai. Login, refresh aur passwords ka flow aage authentication chapter mein detail mein hai.

Chapter 08

Middleware: request ke aage-peeche kya chalta hai?

src/backendfastapi/core/middleware.py / exact excerpt from RequestContextMiddleware
headers = dict(scope["headers"])
supplied = headers.get(b"x-request-id", b"").decode("latin-1")
request_id = supplied if request_id_pattern.fullmatch(supplied) else uuid4().hex
scope.setdefault("state", {})["request_id"] = request_id
started = perf_counter()
status_code = 500

Yeh pure ASGI middleware hai. scope mein request method, path, headers aur shared request state jaise connection metadata hote hain. receive incoming protocol messages deta hai; send outgoing messages bhejta hai. Non-HTTP scopes unchanged aage pass hote hain. Middleware sirf bounded aur restricted format ka request ID accept karta hai, warna naya ID generate karta hai. scope["state"] hi Starlette ke through request.state ke naam se milta hai.

Response interception / exact excerpt
async def send_with_context(message: Message) -> None:
    nonlocal status_code
    if message["type"] == "http.response.start":
        status_code = message["status"]
        message["headers"] = list(message.get("headers", [])) + [
            (b"x-request-id", request_id.encode()),
            (b"x-content-type-options", b"nosniff"),
            (b"x-frame-options", b"DENY"),
            (b"referrer-policy", b"no-referrer"),
        ]
    await send(message)

nonlocal se nested function enclosing request ka status variable update kar sakta hai. HTTP headers ek baar http.response.start mein bheje jate hain; body chunks alag messages hote hain. send wrap karne se streaming response ko buffer kiye bina headers badal sakte hain. Bahar ka finally completion, duration, status, request ID aur trace ID log karta hai, chahe inner app se exception nikle.

Body limit: RequestBodyLimitMiddleware malformed declared length ko 400 aur oversized declared/actual body ko 413 se reject karta hai. JSON parsing se pehle configured limit tak hi body buffer hoti hai. Content-Length missing ho tab bhi chunks count hote hain. Phir replay function bounded body inner app ko deta hai. Yeh jaan-boojhkar bounded buffer hai, unlimited streaming-upload implementation nahi.

Incoming request par user middleware ka order Kya karta hai
1. RequestTracingMiddleware HTTP trace context establish karta hai
2. RequestContextMiddleware Request ID, security headers, access logs
3. HttpMetricsMiddleware Counts, latency, in-progress requests
4. CORSMiddleware Browser origins aur preflight requests handle karta hai
5. TrustedHostMiddleware Allowed Host headers check karta hai
6. RequestBodyLimitMiddleware App parsing se pehle request body bound karta hai

Jo user middleware last register hota hai, woh outermost hota hai; response wapas bahar ki taraf aata hai. Framework ki error-handling layers bhi is stack ko wrap karti hain. Middleware early return kar sakta hai, isliye invalid preflight ya oversized request routing/authentication tak na bhi pahunche. CORS non-browser client ko nahi rokta aur authentication mechanism nahi hai.

Dependencies se difference: middleware general request/response concerns handle karta hai, unmatched paths par bhi. Dependencies selected routes ki requirements batati hain aur typed values inject kar sakti hain. Protected principal ek dependency hai, middleware nahi.

Chapter 25

App ko teen passes mein padho

Pehla pass: ek ticket, abhi agent complexity nahi

  1. Entry point padho aur alag karo: import time, app construction, startup, request time aur shutdown par kya hota hai.
  2. Settings padho. Predict karo ki first call se pehle aur baad mein environment variable badalne ka kya effect hoga.
  3. Router registration se ticket endpoint, input/response models, session dependency, service aur repository tak follow karo.
  4. Khud explain karo: tenant ID kahan establish hota hai, transaction kahan commit hoti hai, aur response har ORM attribute expose kyon nahi karta.

Doosra pass: failures aur boundaries

Predict karo: short message, unknown JSON field, authenticated mode mein missing bearer token, viewer ka PATCH, doosre tenant ka ID, stale ticket version, changed input ke saath repeated idempotency key aur oversized body par kya hoga? Phir har result prove karne wali code branch aur corresponding test dhoondho. Validation ko authorization mat samjho.

Teesra pass: durable work

Run submission ko replay, prompt selection, budget reservation, commit, worker claim, graph nodes, persisted events, tool approval aur final settlement tak trace karo. Socho: job accept hone ke baad API restart ho, generation ke beech worker band ho, SSE dekhte waqt user logout kare, ya graph recovery se pehle tool receipt already ho, to kya hoga?

Self-check: bina dekhe yeh differences samjha sakte ho?
  • get_settings() configuration return karta hai; Depends(get_settings) FastAPI se usko supply karne ko kehta hai.
  • app.state app-local memory hai; request.state request-local context hai.
  • flush durability nahi; commit transaction ki durability boundary hai.
  • JWT signature claims verify karta hai; live database session aur current role access abhi bhi decide karte hain.
  • async cooperative I/O concurrency deta hai; blocking code ko automatically nonblocking nahi banata.
  • 202 acceptance hai, partial SSE text progress hai, aur succeeded committed completion hai.
  • Checkpoints completed work repeat hona kam karte hain; exactly-once provider billing guarantee nahi karte.

Aage existing learning path, HTTP foundations, Pydantic lesson aur async/concurrency lesson padho. Yeh guide current code ka map hai; tests ya platform ki explicitly bounded guarantees ka replacement nahi.
